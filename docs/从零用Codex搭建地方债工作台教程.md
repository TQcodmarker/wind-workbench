# 零基础用 Codex 做项目：通用方法与地方债工作台案例

> 适合完全不会使用 AI 编程工具的人。先学习一套可以复用到任何项目的方法，再用本仓库的地方债工作台作为完整案例。  
> 核心原则：你负责业务判断和验收，AI 负责提问、整理、设计、编码、测试与解释；关键业务规则不清楚时，不能让 AI 自行猜测。

## 第一部分：做一个项目的通用方法

```text
明确需求与 AI 角色
        ↓
反问澄清，尤其确认数据源和数据处理逻辑
        ↓
PRD.md（需求文档） ← 复审确认
        ↓
design.md（设计文档） ← 确认风格与交互
        ↓
可点击 Demo（先验证产品形态）
        ↓
SDD + TDD 正式开发
        ↓
数据、前端、逻辑、性能四层优化
```

SDD（Specification-Driven Development）是“基于规格/文档开发”：先写清功能和验收标准，再让 AI 按文档实现。TDD（Test-Driven Development）是“测试驱动开发”：先写输入与预期输出的测试，再写让测试通过的代码。两者一起使用，能避免页面看似能用、数据却不正确。

### 阶段 1：明确需求，并定义 AI 此刻的角色

不要一开始就说“帮我做一个系统”。先说明谁要使用、要解决什么问题、什么不能出错，并为 AI 定义当前需要的角色。角色应随阶段切换：

| 你正在解决的问题 | 应定义的 AI 角色 | 主要产出 |
| --- | --- | --- |
| 想法还模糊 | 产品经理、业务分析师 | 问题清单、用户流程、范围边界 |
| 数据与口径不清楚 | 领域专家、数据分析师 | 数据源方案、字段字典、处理规则 |
| 想确认页面体验 | 产品设计师、UI 设计师 | 页面结构、交互、视觉规范 |
| 需要做浏览器页面 | 前端工程师 | 页面、筛选、表格、导出与交互 |
| 需要取数、计算、保存 | 后端工程师 | 接口、数据库、任务、计算逻辑 |
| 需要验证正确性 | 测试工程师、审计员 | 测试、边界清单、验收证据 |

需求阶段要明确允许 AI 反问。你不必一开始就懂全部答案，但业务未决定的地方必须标为“待确认”，而不是由 AI 替你决定。

可直接使用这段首轮提示词：

```text
你现在是我的 [产品经理 / 领域专家]。我是零基础用户，想做一个 [项目名称]。

初步想法：
- 使用者是谁：[谁]
- 最常做的事：[三件以内]
- 希望解决的问题：[问题]
- 已知数据来源：[来源，未知可写待确认]
- 最不能出错的规则：[规则]
- 不希望系统做的事：[边界]

请先不要写代码，也不要替我猜业务规则。
请用通俗语言反问我，优先追问会影响数据源、数据处理逻辑、结果口径、权限和验收方式的问题；每轮最多问 5 个问题。等我回答后继续澄清，直到你能总结出明确的需求清单。
```

金融与数据类项目，开发前优先确认：数据是否有授权、实时/日终/历史的定义、字段与单位、目标日期和实际观测日期、缺失值与有效零值的区别、去重与筛选规则、汇总公式、失败时的数据保留策略、样本与完整覆盖的边界。没有这些答案时，只能做明确标注的 Demo，不能把结果说成真实完整数据。

### 阶段 2：需求明确后，生成并复审 `PRD.md`

PRD（Product Requirements Document）是开发契约，不是宣传文案。它应该让任何新加入的人无需翻聊天记录，也能知道做什么、不做什么、数据怎样处理、怎样验收。

```text
你现在是产品经理。请把我们已确认的内容写成项目根目录的 PRD.md。
不要补充未经确认的业务假设；不确定处标为“待确认”。

PRD 必须包含：
1. 背景、目标用户和要解决的问题；
2. 功能范围与非目标；
3. 用户流程和页面清单；
4. 数据源、字段字典、更新方式；
5. 数据处理逻辑：输入、筛选、计算、输出、异常处理；
6. 权限、安全与数据边界；
7. 验收标准及至少 3 个可手算的示例；
8. 风险、待确认事项和版本记录。

写完后先用清单让我复审，不要开始开发。
```

复审 PRD 时，重点检查：每个数字是否说清来源、口径、时间和计算方式；空值与 0 是否有定义；“希望如此”是否被误写成“已经实现”；每个按钮成功、失败、无数据时会发生什么；AI 按这份文档做出来是否就是你心中的产品。金融项目里，数据处理逻辑比页面文案更应逐条复审。

### 阶段 3：同步编写 `design.md`，服务前端开发

PRD 说“做什么”，`design.md` 说“用户如何看到和操作”。两份文档要同步维护：PRD 增加筛选条件，design 也应补上筛选位置、空状态、失败提示和窄屏表现。

```text
你现在是产品设计师和 UI 设计师。请依据 PRD.md 生成 design.md。
我的设计风格是：[例如：简洁、干净、专业、低干扰、金融终端感]。

design.md 必须包含：信息架构和导航；每页区块、字段、按钮和交互；颜色、字号、间距、表格和状态标签；加载、空数据、失败、长任务进度；桌面端与窄屏处理；键盘与无障碍要求；可点击 Demo 的验收清单。
先给出页面结构，不要写前端代码，等我确认。
```

“简洁干净”还需要继续量化：什么最先显示、什么可以折叠、用户如何知道当前筛选范围、危险状态怎样被看见、超宽表格怎么滚动而不丢上下文。

### 阶段 4：先做 Demo，再按 SDD 与 TDD 开发

Demo 阶段先验证产品形态：页面结构、点击路径、筛选、详情、空状态和错误提示。可以使用明确标注的模拟数据，不急着接真实数据源，也不应保存真实密钥。

```text
你现在是原型设计师和前端工程师。请依据 PRD.md 与 design.md 做可点击 Demo。
只使用明确标注的模拟数据，不连接真实数据源，不保存真实密钥。
实现关键页面、筛选路径、详情抽屉和加载/空/失败状态；完成后告诉我如何操作，并列出它与正式版本的差异。
```

确认 Demo 后进入正式开发：每次只实现一个小功能，并要求 AI 标出对应的 PRD/design 条目。数据处理逻辑尤其使用 TDD：先给出测试数据、预期结果和边界情况；先运行测试确认它会失败；再用最小实现让测试通过；最后运行相关全部测试。

```text
你现在是测试工程师和 [前端/后端] 工程师。请按 TDD 实现 [规则/功能]。
先写测试数据、预期结果和边界场景；先确认新测试在实现前失败；再写最小实现使其通过；最后运行相关全部测试。不得为了通过测试删除边界场景。
```

### 阶段 5：优化阶段，按四层逐一核对

优化不是笼统地“再优化一下”，而是先选定目标与证据。

| 优化层 | 需要核对的内容 | 验证方法 |
| --- | --- | --- |
| 数据正确性 | 来源、单位、日期、口径、计算 | 手算样本、来源回放、自动测试 |
| 处理逻辑 | 过滤、去重、缓存、失败恢复、历史隔离 | 边界测试、重试、数据库核对 |
| 前端体验 | 筛选清晰度、表格可读性、错误说明 | 走查、截图、窄屏测试 |
| 性能稳定性 | 大数据、慢接口、重复点击、长任务 | 性能基线、分页、进度与恢复测试 |

```text
你现在是性能工程师和代码审计员。请只读检查当前项目的 [数据/逻辑/前端/性能] 优化层。
目标是：[一个可衡量目标]。先给出现状证据、问题排序、最小改动方案和回归风险；等我确认后再修改。优化后用同一组测试或指标对比前后结果，不能只说“应该更快”。
```

## 第二部分：将这套方法应用到当前地方债工作台
### 当前地方债工作台的实操补充

> 适合对象：没写过代码、第一次使用 AI 编程工具的人。  
> 目标：在自己的 Windows 电脑上，用 Codex 做出一个“能看数据、能筛选、能导出、能追溯来源”的本地工作台。本文以本仓库的地方债行情工作台为例，但方法同样适用于销售看板、库存看板、项目管理台等业务工具。

## 先说清楚：你要做的不是“让 AI 一次生成一个网站”

把 Codex 当作一位会写代码、会读文件、会执行测试的开发搭档，而不是许愿机。你负责说明业务目标、确认关键选择、验收页面；Codex 负责把需求拆成代码、修改项目、运行检查并解释结果。

一个可用的工作台通常由四层组成：

```text
浏览器页面（表格、筛选、按钮）
        ↓
本机接口（接收页面请求、校验输入）
        ↓
业务规则（分组、计算、筛选、汇总）
        ↓
本地数据（SQLite 数据库、任务记录、原始证据）
```

本项目的实际技术组合是：前端使用 React、TypeScript 和 Vite；后端使用 Python FastAPI；SQLite 保存本机数据；AKShare 或 Wind 提供数据。你不必在一开始理解这些名词，只需知道：前端是看得见的页面，后端负责计算和取数，数据库负责把结果留在电脑里。

## 0. 开始前的准备

### 你需要准备什么

- 一台 Windows 电脑，能联网。
- Codex 桌面版或你所在团队允许使用的 Codex 环境。
- Node.js 20.19 或更高版本（推荐安装 Node.js LTS）。
- Python 3.11 或更高版本。
- 一个文件夹，例如 `D:\code\地方债工作台`。
- 一份业务说明：你要看什么数据、按什么维度筛选、怎么算、谁来使用。

如果你做的是本教程中的地方债工作台，AKShare 可作为公开数据入口；若要连接 Wind，则还需要自己拥有合法可用的 Wind Key。不要把 Key、密码、Cookie 或客户数据直接粘贴到聊天记录、代码仓库或截图中。

### 安装后如何自检

打开 PowerShell，依次输入：

```powershell
node --version
npm --version
python --version
```

每条命令都应输出版本号。若提示“不是内部或外部命令”，说明还没安装好，或安装后没有重新打开终端。

### 给 Codex 的第一条消息

在 Codex 中打开你的项目文件夹，然后直接说：

```text
我是零基础。请先不要写代码，先检查当前项目有哪些文件、能否启动、使用了什么技术栈。
请用非技术语言告诉我：这个项目已经能做什么、还缺什么、我下一步应该如何验证。
不要读取或输出任何密钥、账号、个人数据。
```

这一步很重要。先让 AI “体检”，再改代码，能避免在错误的目录里工作或误删已有内容。

## 1. 先写需求，不要先让 AI 画页面

零基础用户最常见的困难不是不会写代码，而是需求只停留在“做一个像 XX 的工作台”。这会让 AI 猜测，结果页面也许漂亮，却不能用。

先复制下面的模板，方括号内换成你的业务内容。写不完整也没关系，可以标记“待确认”。

```text
项目名称：[例如：地方债行情工作台]
谁使用：[例如：债券研究员和销售支持]
用户要完成的三件事：
1. [例如：按评估日期查看各地区、期限和债券类型的收益率]
2. [例如：筛选某地区后查看参与计算的债券和来源]
3. [例如：导出当前筛选结果为 CSV]

数据从哪里来：[例如：AKShare；有权限时可切换 Wind]
数据是否允许出电脑：[例如：不允许，只能本机运行]
核心计算规则：[例如：同组债券按发行规模加权平均]
必须筛选的维度：[例如：日期、发行日期组、地区、期限、一般债/专项债]
空数据怎么显示：[例如：显示“—”，不能把 0 当作空值]
需要保留什么证据：[例如：原始响应、采集时间、字段来源、失败原因]
不做什么：[例如：不提供投资建议；不把样本说成全国完整覆盖]
验收方式：[例如：挑 3 个分组，用 Excel 手算后与页面对比]
```

然后把它发给 Codex：

```text
下面是我的需求草稿。请先把它整理成一页“需求确认清单”，指出会影响结果的歧义，最多问我 5 个关键问题。
在我确认前，不要修改代码，也不要自行假设数据覆盖范围或业务口径。

[粘贴上面的需求草稿]
```

### 地方债案例中必须确认的口径

本仓库不是简单地把一张表搬到网页上，它有明确的数据边界。若你做同类工具，至少要确认：

| 问题 | 本项目采用的做法 | 为什么要先确认 |
| --- | --- | --- |
| 收益率是什么 | AKShare 使用公开成交收益率；Wind 使用各自保存的口径 | “收益率”不是一个唯一字段 |
| 如何分期限 | 以计算或验证后的期限/久期分到 3、5、7、10、15、20、30 年档 | 不能凭列名随意归档 |
| 如何汇总 | 同一组内按发行规模加权 | 算术平均和加权平均会得到不同结果 |
| 没有数据怎么办 | 保存为空，页面显示“—” | 0 是可能存在的有效值，不能混淆 |
| AKShare 是否等于全国完整行情 | 不是；目录、静态资料、当日成交、可汇总是不同覆盖层次 | 防止把部分样本误称为完整市场 |
| AI 是否直接决定数值 | 不决定；查询、差值、排序由程序计算 | 让 AI 负责理解问题和组织文字，而非编造数值 |

## 2. 把需求拆成小里程碑

不要要求“现在把所有功能做完”。更稳妥的顺序是每次只交付一个可验证的小成果。

```text
里程碑 1：能启动一个本地页面，显示静态示例表格
里程碑 2：能从后端读取一条或几条真实/演示数据
里程碑 3：实现业务计算，并用单元测试验证
里程碑 4：加入筛选、详情和 CSV 导出
里程碑 5：保存到本机 SQLite，重启后仍能看到历史
里程碑 6：接入数据源，展示来源与失败状态
里程碑 7：加入自然语言查询，但数值仍由程序计算
里程碑 8：做安全、错误提示、性能和人工验收
```

每个里程碑都可以用这一段提示词：

```text
请只完成里程碑 [编号/名称]，不要顺手重构无关代码。
开始前先告诉我：你准备改哪些文件、页面上我能看到什么变化、如何验证。
完成后请：
1. 列出实际修改的文件；
2. 运行与本次改动相关的检查；
3. 告诉我我在浏览器里应该点哪里；
4. 说明已知限制和下一步建议。
若需要新增依赖、联网下载、删除数据或使用密钥，先说明用途并等待我确认。
```

## 3. 从零建立项目：让 Codex 先做“最小可运行版本”

如果你没有现成代码，可以在空文件夹中给 Codex 以下任务：

```text
请在当前空文件夹创建一个“本机运行的地方债工作台”最小版本。
技术约束：React + TypeScript + Vite 前端，Python FastAPI 后端，SQLite 本地存储。
第一版不要接真实数据源，不要接大模型，不要登录功能。
只做：一个日期选择器、一个地区筛选、一个三行的示例汇总表、一个“查看详情”抽屉。
请先给出目录结构和启动方案，等我确认后再创建文件。
```

确认后，再让它执行实现。完成的最小目录大致应有：

```text
src/                 页面与样式
backend/             接口、计算与存储
tests/               自动化测试
docs/                需求、使用说明、口径说明
start.ps1            Windows 一键启动脚本
package.json         前端依赖与命令
requirements.txt     Python 依赖
```

你不需要手工创建每个文件；关键是要求 AI 解释每个目录的职责，并避免把所有逻辑都塞到一个超大的文件中。

## 4. 本项目如何启动和验收第一屏

在本仓库根目录打开 PowerShell，运行：

```powershell
.\start.ps1
```

脚本会检查依赖、构建前端并启动本机服务。看到服务正常运行后，在浏览器打开：

```text
http://127.0.0.1:8765
```

`127.0.0.1` 的意思是“只在你的这台电脑上访问”，不是公网网址。按 `Ctrl+C` 可停止网页服务；本机 SQLite 中已保存的历史不会因停止服务而自动消失。

第一次打开时，按照这个清单验收：

- 页面能打开，且没有持续转圈或白屏。
- 能看到当前选中的数据源；首次真实数据库默认是 AKShare。
- 改变日期或筛选条件后，表格、空状态和筛选标签能一致更新。
- 点击表中数值能打开详情，能看到样本、计算依据或来源信息。
- 空组显示“—”，而不是 `0`、`NaN` 或空白。
- 导出的 CSV 与当前筛选条件一致。

若页面打不开，把浏览器报错和终端最后约 30 行文字复制给 Codex，并这样提问：

```text
我按启动步骤操作后页面打不开。请先诊断，不要直接大规模修改。
请按“现象 → 最可能原因 → 需要我提供的证据 → 最小修复方案”回答。
这是终端最后的输出：
[粘贴输出]
```

不要把一整屏包含密钥的日志直接贴出。先检查是否有 `key`、`token`、`Authorization`、手机号、客户名等敏感字段。

## 5. 用好 Codex 的四种提问方式

### A. 让它解释现有项目

```text
请带我阅读这个项目。先从用户在浏览器点击“更新数据”开始，画出数据经过哪些前端文件、接口、业务函数和数据库表。
每一步用一句人话解释；最后给出我应该阅读的文件顺序。不要修改文件。
```

### B. 让它新增一个小功能

```text
在“已有个券”页面增加按证券代码或简称搜索的功能。
要求：搜索应由后端分页接口处理；输入为空时保持原列表；不改变既有数据源和计算口径；给出至少 3 个测试场景。
先检查现有分页接口和页面状态，再实施最小改动。
```

### C. 让它修 Bug

```text
问题：切换筛选条件后，导出的 CSV 仍然是上一次的结果。
复现步骤：1. 选择上海市；2. 导出；3. 切换北京市；4. 再导出。
预期：第二次 CSV 只含北京市。
实际：仍含上海市。
请先定位数据从页面到导出接口的路径，写一个会失败的测试，再修复。不要改动无关样式。
```

### D. 让它做代码审查

```text
请审查我最近的改动，不要直接修改。重点检查：
1. 是否会把有效的 0 当作空数据；
2. 是否会把不同日期或不同数据源混在一起；
3. 是否可能泄露 Wind Key；
4. 是否有页面能触发重复采集任务。
按严重程度列出问题，并给出文件和行号依据。
```

好的提示词包含四件事：背景、具体动作、不可违反的约束、完成标准。相比“帮我优化一下”，它更容易得到可验收的结果。

## 6. 数据源接入：先把“来源”和“覆盖范围”做出来

真实数据接入是最容易出错的环节。先要求 Codex 加数据源状态页，再接批量更新，不要反过来。

### 本项目的两类来源

- AKShare：适合作为公开数据入口。它能提供目录、静态资料、公开成交等不同类型的数据，但并不天然等于完整的逐券估值市场。
- Wind：需要合法 Key。项目把 Key 存于当前 Windows 用户的 DPAPI 加密配置库，浏览器不保存也不回显 Key；新任务需要显式验证和取数。

在数据源页面，应同时展示“连接是否成功”和“所需字段是否可用”。连接通，并不等于你能拿到某一天、某只债券、某个口径的数据。

给 Codex 的接入提示词可以这样写：

```text
请为数据源接入增加可审计的状态设计。每次查询至少记录：数据源名称、请求时间、实际观测日期、原始字段名、单位、响应摘要、失败原因和任务 ID。
页面必须区分“连接成功”“有部分样本”“可汇总”“全国完整结果”。
不得用最新行情回填历史日期；不得在 AKShare 无数据时自动改用 Wind。
先给出数据状态模型和验证用例，再改代码。
```

### 不要把密钥交给 AI

正确做法是：让 Codex 实现本地配置输入框、服务端保存和测试按钮；你本人在本机页面中输入 Key。不要把 Key 发在聊天里，也不要写进 `README.md`、`.env.example` 的真实值、测试截图或 Git 提交。

如果 Codex 要求你在终端设置环境变量，请使用临时的、当前窗口有效的方式，并确认终端历史或录屏不会留存密钥。生产或团队环境还需要单独的凭据管理方案。

## 7. 把“计算正确”变成能验证的事实

金融、报表、库存、绩效等工作台，漂亮界面不等于正确。最重要的部分是把业务口径写成测试。

本项目中一个核心公式是发行规模加权平均：

```text
加权收益率 = Σ（单券收益率 × 单券发行规模）÷ Σ（单券发行规模）
```

例如 A 债收益率 2.00%、发行规模 100；B 债收益率 2.50%、发行规模 300，则汇总值是 `(2.00 × 100 + 2.50 × 300) ÷ 400 = 2.375%`。

让 Codex 为每条业务规则写测试时，可以这样说：

```text
请为“发行规模加权汇总”补充单元测试。至少覆盖：
1. 普通两券加权；
2. 有效收益率为 0 的债券必须保留；
3. 发行规模为 0 或缺失时不参与计算；
4. 没有合格债券时收益率为 null、样本数为 0；
5. 同一债券跨市场重复时不能重复计入。
请先展示测试数据和预期结果，再写代码。
```

每当 AI 说“已完成”，都问一句：**“请给我一个我能手算或肉眼核对的例子。”** 这比只看代码更可靠。

## 8. 给工作台加 AI 助手时，怎样避免“AI 胡说”

工作台里的“AI 助手”最好拆成两个职责：

```text
用户自然语言问题
        ↓
解析条件（日期、地区、期限、债券类型）
        ↓
固定程序查询数据库、计算差值、排序   ← 数值以这里为准
        ↓
AI 或模板把已确认结果组织成易读文字
```

本项目现有助手采用“有限中文规则解析 + 模板摘要”，数值、差值和排序均由固定程序计算；大模型配置页只用于测试 OpenAI 兼容服务连接，并不让模型参与行情数值计算。这是一个对零基础团队很友好的起点。

做 AI 功能时给 Codex 的约束应写得非常明确：

```text
请实现自然语言查询入口，但必须遵守：
- 查询只能读取已保存的数据，不能因提问而触发采集；
- 数值、比较差值、排序必须由确定性程序计算；
- 条件不完整时追问，不要擅自选择日期或范围；
- 找不到数据时明确说没有，不能用其他日期替代；
- 回答必须显示实际使用的日期、数据源和筛选范围；
- 不输出投资建议，也不把相关性写成因果关系。
请先写验收案例再实现。
```

## 9. 出错时的“对话式排障”模板

遇到问题时，描述越具体，修复越快。复制这个模板给 Codex：

```text
现象：[页面/接口/导出/计算哪里不对]
我做了什么：[从第 1 步开始列复现步骤]
我期待什么：[预期结果]
实际看到什么：[报错、截图描述、错误数据]
何时开始：[刚修改后/一直如此/仅某日期]
是否影响数据：[是/否/不确定]

请先只做诊断：提出 2-3 个可验证假设，并告诉我每个假设需要看哪个文件、接口响应或日志。
没有证据前不要删除数据库、重置项目或大规模重写。
```

如果涉及本机数据，先让 Codex 导出或备份，再执行具有破坏性的操作。尤其不要随口同意“清空 runtime”“重置数据库”“删除缓存”；这些命令可能会清除历史任务和证据。

## 10. 发布前的验收清单

即使工作台只在本机使用，也建议逐项打钩：

- [ ] 新电脑或新终端能按 README 的命令启动。
- [ ] 页面、接口、构建和关键业务测试均通过。
- [ ] 选择不同日期、数据源后，不会混读数据。
- [ ] 历史数据重启后仍存在；失败的任务不会覆盖已成功结果。
- [ ] 空值、有效 0、无数据、接口失败在页面上有不同说明。
- [ ] 导出数据与当前页面筛选一致。
- [ ] 每个关键数值都能回到来源或计算依据。
- [ ] 密钥不在代码、日志、截图、导出文件和版本库中。
- [ ] 长任务可看到进度，关闭浏览器后不会悄悄丢失。
- [ ] 明确写出了数据覆盖范围、更新时间和不适用场景。

最后可让 Codex 做一次“发布前检查”：

```text
请按发布前验收清单检查当前项目，只读检查，不修改文件。
请把每一项标为“通过 / 未通过 / 需要人工确认”，并给出证据路径。
重点检查本机运行、安全边界、数据来源、空值处理、历史隔离和可追溯性。
```

## 11. 这个项目可直接继续使用的常用命令

在项目根目录运行：

```powershell
# 一键构建并启动本机服务
.\start.ps1

# 后端已经准备好时，直接启动 FastAPI 服务
.venv\Scripts\python.exe -m uvicorn backend.api:app --host 127.0.0.1 --port 8765

# 开发前端：另开一个 PowerShell，后端保持运行
npm.cmd run dev
```

开发前端模式通常访问 `http://127.0.0.1:5173`；完整本机服务访问 `http://127.0.0.1:8765`。后端接口文档在服务启动后可访问 `http://127.0.0.1:8765/docs`，它主要给开发和排障使用，不需要一开始就学习。

## 12. 你接下来可以怎么做

如果你已经打开了这个仓库，推荐按下面顺序与 Codex 对话：

1. “请用零基础能听懂的话带我走一遍首页、数据源、已有个券、全量同步、AI 助手和溯源页面。”
2. “请选一个最小的真实数据样本，带我核对一次从来源字段到页面汇总值的全过程。”
3. “请为我写一份一页纸的日常操作手册：今天更新什么、看到失败怎么办、何时可以导出、何时不能把结果用于完整市场判断。”
4. “我想增加 [一个明确功能]。先问我必要问题，然后按里程碑实现并测试。”

做到这里，你已经掌握了与 Codex 协作的核心能力：把模糊想法变成可验证的小目标，让 AI 每次只做一块，持续检查数据边界和结果依据。真正可靠的工作台，不是 AI 写得有多快，而是每一个展示给业务人员的数字都能说清从哪里来、按什么规则算、什么时候不该使用。
